# RPF-Agent 证书核验功能调研报告

- 日期：2026-11-26
- 范围：在智能评标系统中新增「证书在线核验」能力的可行性、数据源、接入路径与系统设计
- 触发来源：用户提供的参考页 https://www.dkcnas.cn/cx-cnca-cn-certeclou.html
- 状态：调研结论（**含一项阻塞待确认：官方 API 是否真实可用**）

---

## 0. 结论速览

| 问题 | 结论 |
|---|---|
| 参考页给出 API 规格了吗？ | **没有。**该页是实验室咨询公司（德恺）的科普软文，只有一句「2025 年，新增 API 接口，企业可集成到内部系统」，无端点、无参数、无认证方式、无调用示例 |
| 能找到官方公开 API 文档吗？ | **不能。**多轮检索（CNCA 官网、认E云平台、GitHub、数据 API 市场）均未找到任何公开的认证认可证书核验 API 规格 |
| 平台网页能直接程序化查询吗？ | cx.cnca.cn 全站有 **JS cookie 反爬挑战**（HTTP 521 + `__jsl_clearance_s`），逆向可行但有合规与稳定性风险，不建议作为产品主路径 |
| RPF-Agent 现状如何？ | 已有**文档内**证书证据链（证书抽取、复印件定位、查询截图三态检测、编号比对），但**没有对官方登记数据的真伪核验**——这正是本功能要补的洞 |
| 推荐路线 | **双层设计**：先落地「核验工作台 + Provider 抽象 + Mock Provider」（不阻塞、可验收），官方/第三方 API 到位后即插即用；核验结果只作**外部事实**进评分事实链，遵守既有三态与不自动否决口径 |

## 1. 参考页核查（用户指定的 API 来源）

页面：《认证认可业务信息统一查询平台（认E云）：权威指南与实用操作》（2025-09-23，德恺实验室咨询）

### 1.1 页面实际内容

该页是对「认E云」平台（全国认证认可信息公共服务平台，cx.cnca.cn）的介绍性文章，内容要点：

- 平台由国家市场监督管理总局/CNCA 运营，2023 年上线，集成 CMA、CNAS、CCC、ISO 体系认证等数据；
- 四个查询模块：**认证结果查询**（证书真伪/有效期/认可范围）、**从业机构查询**、**从业人员查询**、2025 新增碳足迹查询；
- 网页操作支持批量查询（Excel ≤100 条）、结果导出、微信小程序扫码；
- 平台免费，需手机号注册。

### 1.2 关于「API」的原文

全文关于 API 只有一句话（Tips 段）：

> 「平台免费使用，但需注册账号（手机号验证）。2025 年，新增 API 接口，企业可集成到内部系统，实现自动化查询。」

**没有**任何以下信息：接口地址、请求方法、参数表、签名/鉴权方式、返回字段、调用示例、配额与计费、申请流程。该页还标注「参考来源：www.cnca.gov.cn / cx.cnca.cn」，本身非官方文档。

### 1.3 核查动作与结果

| 动作 | 结果 |
|---|---|
| 抓取该页全文 | 成功；确认 API 仅一句带过 |
| CNCA「互联网+服务」栏目（cnca.gov.cn/hlwfw） | 列出 18 个业务系统入口，**无开放接口/开发者栏目** |
| cx.cnca.cn 首页与结果页探测 | 全部返回 **HTTP 521 + JS cookie 挑战脚本**（反爬），无 REST 端点暴露 |
| cnca.gov.cn 站内搜索网关（jpaas-jsearch） | 200，但那是**站内全文搜索**接口，不是证书核验接口 |
| GitHub 检索（CertECloud / cx.cnca / 认证认可查询） | **0 个**可用客户端项目 |
| Bing 多轮检索（认E云 API、证书核验 API、数据市场、政务数据开放） | 无任何公开 API 文档；结果均为平台官网与科普文 |

**结论：参考页所称 API 无法从公开渠道证实。**它可能指：①平台面向企业的内部合作接口（需商务申请）；②咨询公司自己转售的代查服务；③信息不实。**在拿到官方接口文档之前，不能按「有一个可调的 API」来做确定性设计。**

## 2. 官方平台现状

### 2.1 平台画像

| 项 | 内容 |
|---|---|
| 名称 | 全国认证认可信息公共服务平台（认E云） |
| 入口 | https://cx.cnca.cn/CertECloud/index/index/page |
| 运营 | 国家认监委（CNCA） |
| 数据覆盖 | 认证结果（管理体系/产品/服务认证）、认证机构、认证人员、认可结果（CNAS）、检验检测机构资质（CMA）、监督执法 |
| 查询键 | 证书编号、证书名称、获证组织名称、机构批准号 |
| 返回字段（网页可见） | 证书状态（有效/暂停/撤销/注销）、证书编号、认证项目、认证依据、有效期、获证组织、发证机构 |
| 反爬 | JS 挑战 cookie（`__jsl_clearance_s`），HTTP 521；**无官方公开 API 文档** |
| 费用 | 网页查询免费 |

### 2.2 业务覆盖边界（对评标很关键）

认E云**不覆盖**评标场景中的全部证书类型，接入设计必须按证书族分流：

| 证书族 | 平台可核验？ | 说明 |
|---|---|---|
| ISO 9001/27001/20000 等管理体系认证 | ✅ | 认证结果查询主战场，与本系统 `facts.certificates` 主口径一致 |
| CMA 检验检测机构资质认定 | ✅ | |
| CNAS 实验室认可 | ✅ | 认可结果查询 |
| CCC 强制性产品认证 | ✅ | |
| **CMMI/CSMM 成熟度评估** | ❌ | 属工信部体系（中国电子工业标准化技术协会等评估机构），**不在 CNCA 平台**——系统里 `CMMI` 计分项不能走此核验 |
| 人员证书（CCAA 注册审核员等） | 部分 | 平台有「从业人员查询」，但字段与招投标人员证书（职称/建造师/社保）口径不同 |
| 职称/社保/业绩类材料 | ❌ | 完全不在范围 |

**推论：本功能定位为「ISO/CMA/CCC 族证书的外部事实核验器」，不是万能证书核验。**

## 3. 可选接入路径对比

| 路径 | 描述 | 优点 | 风险/成本 | 判定 |
|---|---|---|---|---|
| **A. 官方 API（商务申请）** | 按软文暗示向 CNCA/平台方申请企业 API | 权威、稳定、合法 | **无公开申请入口**；周期不可控；需先证实其存在 | **首选，但为阻塞项**——先尽调，不等它开工 |
| **B. 网页接口逆向** | 解 `__jsl_clearance_s` 挑战后调 CertECloud 查询端点 | 不依赖商务流程 | 违反平台使用条款的可能性；反爬升级即断；字段脆弱；高频查询有封禁风险 | **不作产品主路径**；至多作内部应急验证手段，且须限速+缓存+可一键关闭 |
| **C. 第三方数据 API** | 聚合数据/阿里云市场等采购「证书查询」类 API | 接入快、有 SLA | 检索未发现**现成的「认证认可证书核验」品类**（多为学历/资格证类）；数据商仍可能回源 cx.cnca.cn，权威性打折 | **备选**：立项前先向 2–3 家数据商询价确认品类存在 |
| **D. 核验工作台（人机协同）** | 系统抽取证书编号→生成核验清单→评委/管理员在认E云网页手工查询→回填结果（截图/状态）→落库进事实链 | 零外部依赖、完全合规、立即可做；把现在「投标人自己贴截图」升级为「本系统留痕的核验记录」 | 仍有人工步骤 | **P0 立即落地** |
| **E. 维持现状** | 仅靠文档内截图/复印件检测 | — | 截图可伪造、无法核真伪；与招标文件「查询结果截图」要求的**真实性**目的有差距 | 不满足需求 |

**推荐组合：D 先行（本期交付）+ A 尽调（并行）+ C 询价（并行）；B 仅在 A/C 均证伪且用户明确授权时作为降级选项。**

## 4. RPF-Agent 现状盘点（证书链路已有什么）

### 4.1 已有能力（文档内证据链）

| 能力 | 位置 | 说明 |
|---|---|---|
| 证书名/编号抽取 | `backend/app/engine/facts.py:66-88`、`material_inventory.py:688-696` | 归一键（ISO9001/27001/20000/CMMI）、`certificate_numbers()` 抽证书编号 |
| 查询截图三态检测 | `engine/objective.py:686` `detect_cert_section()` | 文本标题 + OCR 平台指纹双通道；True/False/**None（盲态，不猜）** |
| 平台详情页判定 | `material_inventory.py:716` `_is_platform_detail_page()` | 品牌指纹 + ≥2 个详情字段（证书编号/有效期/机构批准号…） |
| 逐本复印件定位 | `objective.py:821` `find_cert_copy_pages()`、`classify_cert_backing()` | 每本证书 copy/low/claim 三态背书 |
| 证书编号比对 | `vl_facts.py:239-249` `_cert_number_matches()` | 归一化后精确/后缀匹配，供 VL 事实比对 |
| VL 证书事实契约 | `vl_facts.py:184` `_merge_cert()` | `certificate_number/valid_until/backing` 等结构化字段 |
| 规则侧要求 | 模板 `required_evidence`（如 comprehensive-default.json:402） | 「有效期内证书复印件 + 认E云查询结果截图；无截图不予计分」 |

**现状语义**：系统验证的是「投标人**提交了**复印件和查询截图，且截图长得像平台详情页」，**不验证「该证书在官方数据库里真实存在且有效」**。截图可伪造、可过期、可张冠李戴（编号与持证单位不符）——这是本功能要补的核心洞。

### 4.2 架构可挂载点（与既有设计对齐）

```
┌ 现有评分链 ────────────────────────────────────────────┐
│ facts 抽取 → 三态背书 → objective 计数 → 疑问/冲突转人工  │
└───────────────────────────────────────────────────────┘
                         ▲ 新增：外部事实源（本功能）
┌ 证书核验（新）─────────────────────────────────────────┐
│ 证书清单(编号+名称+单位) →核验 Provider → 核验记录落库    │
│   ├─ Mock Provider（自测）                              │
│   ├─ Official API Provider（待 A 路径就绪）              │
│   ├─ Manual Provider（D：人工回填+截图上传）★本期       │
│   └─ （可选）ReverseWeb Provider（B，开关默认关）        │
│ 结果 → evidence/事实链（矛盾→conflict，不自动否决）       │
└───────────────────────────────────────────────────────┘
```

与项目既有不变量的对齐（**必须遵守**）：

1. **三态语义**：核验结果 = `verified_valid / verified_invalid / unknown`（查无记录、网络失败、平台无此编号族 → 一律 `unknown`，「机器看不见≠不符合」）；
2. **不自动否决**：`verified_invalid` 只产生**建议否决/疑问**（`conflict_flagged`），否决仍是人工确认专属（2026-10-14 用户定调，沿用至今）；
3. **VL 报事实、代码算分**（[[strict-unverified-semantics]]）：Provider 返回结构化事实（状态/有效期/单位名比对），计分仍由 `objective.py` 确定性代码消费；
4. **引文口径分层**（[[evidence-citation-layering]]）：核验记录是**外部事实**，不伪造文档引文；与文档内截图证据并列展示、分别标注来源；
5. **数据出网合规**：现有 `local_endpoint_hosts()` + `allow_remote_confidential()` 白名单机制（`config.py:903-912`）只管 LLM 端点——**新核验 Provider 需要自己的出网开关与主机白名单**，默认关，显式配置才启用；
6. **审计留痕**：每次核验走 `audit_service.log()`（who/when/what/query/result）。

### 4.3 缺什么（功能差距清单）

| # | 差距 | 对应新增 |
|---|---|---|
| G1 | 无证书编号→官方状态的核验通道 | `services/cert_verify_service.py` + Provider 抽象 |
| G2 | 无核验记录存储 | 新表 `certificate_verifications`（`init_db()` create_all 自动建表，免迁移——同 material_tags 先例） |
| G3 | 无核验任务（批量、可取消、有进度） | `jobs` 注册 `verify_certificates` handler（`@register` + `ctx.advance`） |
| G4 | 无核验 UI（清单、回填、截图、结果展示） | Bidders/证据页新增「证书核验」面板 |
| G5 | 核验结果与评分事实链未打通 | `objective.py` 消费 `verified_invalid→疑问`；`cert backing` 增强为「外部核验通过」强证据 |
| G6 | 无出网策略（核验专用） | config 新增 `BID_EVAL_CERT_VERIFY_*` 开关 + 主机白名单 |
| G7 | CMMI 等非 CNCA 族无分流 | 证书族路由表（§2.2），非覆盖族直接标 `not_supported` 不发起查询 |

## 5. 推荐方案设计（P0–P2）

### 5.1 数据模型（新表）

```
certificate_verifications
  id                PK
  project_id        → projects.id
  bidder_id         → bidders.id（可空：也可核验招标要求侧）
  cert_name         原始证书名
  cert_normalized    归一键（normalize_cert 口径）
  cert_number       证书编号（抽取或人工补录，可空）
  holder_name       持证单位（与投标人名比对用）
  provider          mock | manual | official_api | reverse_web
  provider_result    JSON（原始返回，审计用）
  status            verified_valid | verified_invalid | unknown | not_supported
  mismatch_kind     null | number_not_found | holder_mismatch | expired | status_abnormal
  queried_at        查询时间
  evidence_image_id 查询截图/回填附件（manual 路径）
  operator          操作者（manual 路径）
  UNIQUE(project_id, bidder_id, cert_normalized, cert_number, provider)
```

### 5.2 Provider 接口（为未知 API 预留的契约）

```python
class CertVerifyProvider(Protocol):
    name: str
    def supported_family(self, normalized: str) -> bool: ...
    def verify(self, req: CertVerifyRequest) -> CertVerifyResult: ...
    # CertVerifyRequest: cert_name / cert_number / holder_name / normalized
    # CertVerifyResult:  status / raw / matched_fields / fetched_at / error_kind
```

- **ManualProvider（本期实现）**：不发起网络请求；生成待核验清单 + 接受人工回填（状态、截图上传）；`verify()` 仅做本地比对（编号一致性、有效期是否过期、单位名归一比对）。
- **MockProvider**：测试与演示用，固定夹具。
- **OfficialApiProvider**：拿到真实接口文档后实现（预计形态：`POST {base}/cert/query` + appKey/签名 + 证书编号→JSON 状态；**字段以真实文档为准，本报告不臆造**）。

### 5.3 任务与 API

- `POST /projects/{pid}/bidders/{bid}/certs/verify` → 创建 job `verify_certificates`（批量、逐本 `advance`、可取消，沿用现有 job 框架 `jobs/handlers.py`）；
- `GET  .../certs/verifications` → 核验记录列表（含三态与 mismatch_kind）；
- `POST .../certs/verifications/{id}/manual` → 人工回填（operator + 理由必填）；
- 出网类 Provider 调用前过 `config` 白名单闸，未配置直接 `not_supported`。

### 5.4 与评分的接线（保守起步）

- **Phase 1（只读展示）**：核验结果只在 UI 与报告「材料核验」节展示，**不参与计分**——先让评委用起来，避免新数据源扰动既有精度基线（当前验收口径见 eval_suite）；
- **Phase 2（进事实链）**：
  - `verified_valid` + 文档内复印件齐全 → `cert backing` 升级为强证据（等价现有 `section_ok=True` 路径）；
  - `verified_invalid`（number_not_found / status_abnormal / holder_mismatch）→ 该项计分置 `conflict` 疑问 + 报告建议否决，**不自动否决、不自动清零**；
  - `unknown` → 维持现有三态逻辑不变。
- **不改**：价格引擎、排名、基准价剔除逻辑（核验结果不构成「无效标」——无效标政策仍是用户暂缓项 [[invalid-bid-policy-deferred]]）。

### 5.5 合规与风控清单

| 风险 | 缓解 |
|---|---|
| 出网泄露投标数据 | 请求只发**证书编号+单位名**（不发文档内容）；专用白名单默认空=功能关闭；与 LLM 出网闸独立 |
| 平台反爬/封禁 | 主路径不走逆向；若启用 B 路径：单机限速（如 ≤1 次/10s）、磁盘缓存（同 ocr_cache 模式）、熔断开关 |
| API 不存在/中途失效 | Provider 抽象 + `unknown` 降级，评分链不依赖其可用性 |
| 核验结果被当自动否决 | 代码层强制：`verified_invalid` → `conflict_flagged`，沿用 auto_judge 失败降级语义 |
| 证书族误路由 | 路由表（§2.2）：CMMI 等直接 `not_supported`，不发请求、不产生假阴性 |
| 结果时效 | `queried_at` 落库；评分时超过 N 天（建议 30）视为需复核 |
