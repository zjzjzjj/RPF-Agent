# 通用评分规则库设计方案
## ——模板库 + 上传招标方规则逐条覆盖（RPF Agent 扩展）

> **文档定位**：本文回答"系统要有一套通用的招标规则来进行评分，后面通过上传招标方自己的规则与要求进一步定制"应如何落地。目标项目为 `RPF Agent`（智能评标系统），设计在既有"LLM 编译 → 校验 → 签批 → 冻结快照 → 确定性评分"流水线上做**最小侵入**扩展。

>
> 日期：2026-10-10　|　状态：设计稿（未实现）

## 〇、核心结论

**结论一：通用规则库永远不是执行依据，它是"起草加速器 + 覆盖底座"。**
调研报告结论三已锁定四重禁止（《招标投标法实施条例》第四十九条：招标文件没有规定的评标标准和方法不得作为评标的依据；87号令第五十五条：评审因素应当在招标文件中规定并细化量化；财库〔2012〕69号：评审阶段禁止修改或细化评审标准）。调研报告 §2.3 的设计要点原样落进本设计："**P5–P8 只能作为补全候选的来源，不能出现在执行链路里。执行链路只认冻结包内 P0–P4 的来源标记。**"因此模板条目全部标注来源 P5（示范文本），而**冻结的规则包是系统中唯一可执行物**。

**结论二：上传招标文件逐条覆盖，是模板条目唯一的"转正"通道。**
未被文档条款覆盖的模板条目，本质是调研报告六态分级中的 **L4 补全候选**（结论五）——它们必须逐条**签批**（结论四："未签批项一律不可执行"）才能进入冻结包，且在评分输出与报告中**永久标注**"模板兜底（已签批）"。系统绝不把模板兜底静默转成"已核验的文件条款"。

**结论三：对现有架构的侵入极小。**
覆盖 = 对 `criteria` 行的结构化字段替换，不另起炉灶。评分引擎（`backend/app/engine/`）只读冻结快照（`scoring_service._snapshot_criteria`），合并后的规则包结构不变，**引擎核心零修改**，仅透传来源标签。`RPF Agent` 现有冻结链（`rule_service.confirm_package` / `freeze_package` / `new_version`）与校验器通道（`compiler.run_validations`）全部照常工作。

**结论四：编号稳定以模板编号为锚。**
覆盖不换 `code`：被覆盖条目的 `code` 沿用模板 `template_code`（如 `T2.1`）。这样 `diff_versions`（按 code 对齐）、`CODE_DUPLICATE` 校验器、`score_records` 的版本绑定全部照常工作，覆盖前后的对比对人是可读的。

## 一、背景与目标

### 1.1 现状（已核对的代码事实）

- RPF Agent 当前**必须先上传招标文件**才能产出规则包：`backend/app/rules/compiler.py:45` `_load_tender_text()` 对无文档/未解析文档直接抛出 `"只能从招标文件编译规则"`；`POST /projects/{id}/rules/compile`（`backend/app/api/rules.py:40`）只接受 `document_id`。**没有"开箱即用的通用规则"入口。**
- 现行流水线：LLM 抽取（`rules/model.py` `ExtractedCriterion` 契约：quote 逐字、无原文即 null、weight 永不进 prompt）→ 证据核验回填 → 六态分诊（verified / needs_input / ambiguous / gap / conflict / invalid）→ 确定性校验器（`rules/validators.py`）→ 人工逐条确认（`rule_service.accept_criterion:347`）→ confirm（`:430`）→ freeze（`:460`，写 `snapshot_json` + `content_hash`，此后只读）。
- 评分只认冻结快照：`scoring_service.execute_run` → `_snapshot_criteria`（`scoring_service.py:107`），`score_records` 记录 `rule_version` + `package_content_hash`（`scoring_service.py:333`）。

### 1.2 目标（三阶段）

| 阶段 | 目标 | 价值 |
|---|---|---|
| **S0** | 新建项目即可选一份通用评标办法模板（综合评分法-货物/工程/服务、最低评标价法），一键实例化为草稿规则包，**不依赖招标文件**即可完成预览、签批、冻结、演示评分 | 产品开箱可用；演示/培训/测试有合法标注的完整链路 |
| **S1** | 上传真实招标文件编译后，系统自动将编译条目与模板条目**逐条匹配**，人工确认匹配对后**逐条覆盖**；未覆盖处模板条目保留为"模板兜底"，未匹配的编译条目作为文档来源条目追加 | 真实项目主路径：上传文件 → 逐条定制 → 兜底签批 |
| **S2** | 合规红线（价格/否决/资格类模板兜底未签批 → 阻断冻结）+ 评分矩阵与评标报告**逐项标注依据来源** | 每个分都能回答"依据是文件条款还是签批的模板兜底"，可对外举证 |

### 1.3 法定约束与设计落点对照

| 约束 | 出处（调研报告） | 本设计的落点 |
|---|---|---|
| 评审只能用招标文件载明的标准 | 结论三（`c01.py`，引实施条例49条、87号令55条、财库〔2012〕69号） | 冻结包是唯一可执行物；每条 criterion 带 origin/模板溯源；freeze 前置校验 |
| 来源优先级 P0–P8，被采纳须记录"压过了哪一条" | §2.3（`c02.py`） | `override_records.won_source/lost_source`；模板（P5）不进执行链路 |
| 未签批项一律不可执行 | 结论四（`c01.py`） | `signoff` 动作 + `TEMPLATE_FALLBACK_SIGNOFF` 校验器 + `_blocking_items` 拦截 |
| L3/L4 不得自动补全后执行 | 结论五、§4.4 留白机制（`c04.py`） | 模板兜底条目状态 `needs_signoff`，签批前不可冻结 |
| 资格条件"可推荐但不得自动生效"、禁止倾向性条款 | §4.4 生成禁区（`c04.py`） | 模板库不收录品牌/指向性条目；资格类条目默认 `veto_consequence` 待覆盖确认 |

## 二、总体架构

```
┌────────────────────────────────────────────────────────────────────┐
│ 前端（React + AntD）                                                 │
│  ProjectList(选基线模板) · TenderRules(来源chip/覆盖率进度/           │
│  签批队列/匹配提案审核) · ScoreMatrix(依据标注)                       │
└──────────────────────────┬─────────────────────────────────────────┘
                           │ REST /api
┌──────────────────────────▼─────────────────────────────────────────┐
│ API 层  新增：GET /rules/templates · POST …/rules/instantiate ·      │
│  /match-proposal · …/signoff · GET …/coverage                        │
│  变更：compile 增加 mode=merge                                        │
├────────────────────────────────────────────────────────────────────┤
│ 服务层  rule_service(状态机不变) + 新 library_service / merge_service │
├──────────────┬───────────────┬──────────────────┬──────────────────┤
│ rules/library│ rules/merger   │ rules/compiler    │ rules/validators │
│ 模板JSON+加载 │ 确定性匹配      │ (不变；merge 模式  │ (现有)           │
│ schema+hash  │ LLM辅助匹配     │  复用既有抽取产物) │ +2 条 origin 分支 │
│              │ 覆盖执行        │                   │ 校验器           │
├──────────────┴───────────────┴──────────────────┴──────────────────┤
│ engine/ 零修改（只读冻结快照）；快照 schema 升级 rule_package/v2，      │
│ criteria 增加 origin/template_code 等溯源字段，评分落库透传            │
└────────────────────────────────────────────────────────────────────┘
```

**三条互不交叉的数据流**（这是"审计时能切分责任"的结构保证）：

1. **模板路径（P5，不可直接执行）**：库文件 → `instantiate` → 草稿包（origin=template, status=needs_signoff）→ 逐条签批 → confirm → freeze。
2. **文档路径（P1–P4，现行路径，不变）**：upload → parse → compile → 六态分诊 → 人工处置 → confirm → freeze。
3. **覆盖路径（S1）**：compile(mode=merge) → 匹配提案 → 人工确认 → 覆盖执行（模板条目升级为 document 来源，写 `override_records`）→ 兜底条目进签批队列 → confirm → freeze。

三条路径最终都汇聚到**同一个冻结动作**（`rule_service.freeze_package`），因此"演示包"与"真实包"走同一条代码路径，不存在演示旁路。

## 三、通用规则库设计（内容模型）

### 3.1 存储形态：仓库内 JSON 文件，不做 DB 表

采用 `tender-evaluation-assistant` 已验证的形态（`app/rulesets/templates/*.json` + `library.py` 加载器 + README 约定"ships with the image"、`/health` 报告加载数量）：

- 位置：`backend/app/rules/library/templates/<template_id>.json`，**文件名必须等于 `template_id`**（加载器强校验）。
- 加载器：`backend/app/rules/library/loader.py`，提供 `load_templates() -> dict[str, RuleTemplateFile]`、`get_template(tid)`、`library_status()`；坏文件 fail-fast（缺字段/校验不过即启动期报错，不让坏模板流入运行时）。
- **不建 `rule_templates` DB 表**（S0–S2 都不做，仅预留）：模板是随代码评审、随 git 溯源、随镜像发布的资产；只有出现"租户级自定义库"需求时才引入 DB 表 + loader 双源（见 §十一 开放问题 1）。

### 3.2 模板文件 schema

新增 `backend/app/rules/library/schema.py`（Pydantic）。形状**对齐 RPF Agent 既有的 `Criterion / CriterionLevel / CriterionCheck / PriceFormula`**，使覆盖是结构化的字段级替换，而非自由文本映射：

```json
      "template_code": "T3.1",

    },
    {
      "template_code": "T5.1",
      "category": "commercial",
      "name": "同类项目业绩",
      "score_type": "count",
      "max_score": 5,

```

**字段规则**（写成 schema 的 `model_validator`，仿 tender-evaluation-assistant `Template._consistent` 的风格）：

| 规则 | 理由 |
|---|---|
| `template_code` 模板内唯一，格式 `T<分类号>.<序号>`（1=资格 2=符合性 3=价格 4=技术 5=商务） | 编号稳定锚（结论四） |
| 主观项 `levels` 必须通过与 `validators.py` 的 `_check_level_closure` / `_check_level_monotonic` 同构的检查（最低档下界=0、区间连续不重叠、最高档上界=max_score） | **库文件在 CI 里直接用 `validators.py` 的函数做单测**，保证实例化后不被既有校验器卡死 |
| `is_veto=true` 时 `veto_consequence` 必填且 `max_score` 必须为空 | 对应现有 `VETO_CONSEQUENCE_MISSING` / `VETO_SCORED` 校验器 |
| price 类 `formula` 必填 `formula_type / benchmark_method / k` | 对应 `PRICE_PARAMS_INCOMPLETE` |
| **模板条目不携带 quote / source_node_id** | 模板无原文——这是模板条目与文档条目的本质区别；`QUOTE_REQUIRED` 校验器按 origin 分支豁免模板条目（§6.1），改由 `TEMPLATE_FALLBACK_SIGNOFF` 承担其"依据缺失"的警示 |

### 3.3 内置库内容（首发 4 个模板）

| template_id | 名称 | 要点 |
|---|---|---|
| `comprehensive-goods` | 综合评分法（货物） | 价格 30（87号令55条：货物项目价格权重≥30%）、技术 ~45、商务 ~20、资格/符合性否决项 6–8 条 |
| `comprehensive-works` | 综合评分法（工程） | 参照工程评标惯例组织条目；notes 中明示政采与工程招标两套制度分支的适用差异（调研报告对两分支的张力有专门提示） |
| `comprehensive-services` | 综合评分法（服务） | 价格 ≥10%；服务类主观项占比更高 |
| `lowest-price` | 最低评标价法 | 资格 + 符合性否决项 + 价格分 `lowest_ratio`；**无**技术/商务评分项 |

统一约定：criteria 覆盖全部 5 类 category（qualification/compliance/price/technical/commercial）；主观项统一四档（优/良/一般/差）；判据文字一律标注"通用判据，覆盖时替换"。**库内不收录任何品牌、型号、指向唯一供应商的参数类条目**（调研报告 §4.4 生成禁区二——模板库自己不能成为倾向性条款的来源）。

### 3.4 库自身版本与溯源

- `library_version`（语义版本，模板文件变更时手动递增）+ 模板级 `content_hash`（对整个模板 JSON 做 canonical JSON 的 sha256，取前 12 位，与 `rule_service` 现有 `content_hash` 口径一致）。
- **实例化即快照**：`instantiate` 把 `template_id + template_code + template_hash + library_version` 盖到每条 criterion 上。此后**库文件升级不影响已实例化的包**——只在新建项目时生效；旧包要用新库版本，走现有 `new_version` + 重新匹配流程。这与"冻结包不可变"是同一条设计原则在库侧的延伸。

## 四、项目初始化与模板实例化

### 4.1 数据模型变更

**`rule_packages` 新增列**（`db/models.py:140`）：

| 列 | 类型 | 说明 |
|---|---|---|
| `origin` | String(16)，default `'document'`，CHECK `IN ('document','template','merged')` | 包的初始来源 |
| `template_id` / `template_hash` / `library_version` | String，nullable | 实例化自哪个模板的哪个版本 |

**`criteria` 新增列**（`db/models.py:171`）：

| 列 | 类型 | 说明 |
|---|---|---|
| `origin` | String(16)，default `'document'`，CHECK `IN ('template','document','manual')` | **当前生效**来源（覆盖后由 template → document） |
| `template_code` | String(64)，nullable | 模板原始编号；被覆盖时**保留**且与 `code` 相等（编号稳定锚） |
| `template_hash` / `library_version` | String，nullable | 溯源：来自哪个模板版本 |
| `override_json` | JSON，nullable | 最近一次覆盖详情 `{overridden_template_code, match_method, similarity, document_node_id, document_quote, won_source, lost_source, by, at, reason}`（平行于既有 `edit_json` 模式） |
| `signoff_json` | JSON，nullable | `{by, at, reason}`，模板兜底条目的签批记录 |
| `p_source` | Char(2)，nullable | 'P5'（模板）；'P1'–'P4'（文档，按材料类型：正文=P1、附表评分表=P2、规格书=P3、补遗=P4）；NULL（人工新增） |

**`criteria.status` CHECK 扩充两个值**：

- `needs_signoff`：模板兜底待签批。不复用 `needs_input`——"文档没说清"与"文档没规定、用模板兜底"是法律含义完全不同的两件事（开放问题 2 已确认新增）。
- `retired`：人工判定"本项目无此项"，**不进快照、不参与计分**。

既有 `_blocking_items`（`rule_service.py:425`，凡 `status != 'verified'` 即阻断 confirm/freeze）**无需改动**即自动把 `needs_signoff` 挡在外面——这是把新约束接进既有闸门而非另建闸门。

**新表 `override_records`**（覆盖审计；独立于 criteria 行内 `override_json`，供包级时间线与 `new_version` 复制）：

```
override_records(
  id, package_id,
  action,                    -- override | keep_template | drop_template | append_document
  template_criterion_id,     -- 模板来源条目
  document_criterion_id,     -- 临时编译包中的文档条目
  match_method,              -- exact | deterministic | llm | human
  similarity,                -- Numeric(6,4)
  won_source, lost_source,   -- 'P1'..'P4' / 'P5'，记录"压过了哪一条"（调研 §2.3）
  document_id, document_node_id, document_page, quote,   -- 覆盖依据的文件原文
  confirmed_by, reason, created_at
)
```

### 4.2 API 与流程

新增端点（挂进 `backend/app/api/rules.py` 既有 router）：

| 端点 | 说明 |
|---|---|
| `GET /rules/templates` | 模板目录：`[{template_id, name, method, library_version, criteria_count, categories_summary}]` |
| `GET /rules/templates/{template_id}` | 完整条目预览（前端选模板时展示） |
| `POST /projects/{project_id}/rules/instantiate` | body `{template_id}`，**同步执行**（纯确定性复制，无需走 jobs 队列） |
| `POST /rules/criteria/{criterion_id}/signoff` | body `{reason}`（必填），模板兜底签批（§6.2） |
| `GET /rules/packages/{package_id}/coverage` | 覆盖率报告（§6.3） |

**`instantiate` 流程**（新增 `library_service.instantiate_template`）：

1. 校验项目尚无规则包（S0 不支持换模板，见开放问题 5）；取当前最大 version + 1，建 `RulePackage(status='draft', origin='template', source_document_id=None, template_id=…, template_hash=…, library_version=…)`；
2. 逐条复制模板 criteria → `Criterion(origin='template', code=template_code, template_code=template_code, status='needs_signoff', p_source='P5')`；同时落 `CriterionLevel`（档位区间来自模板）、`CriterionCheck`、`PriceFormula`；
3. 更新 `Project.method` 为模板 `method`；
4. 写 `ReviewRecord(action='instantiate')` + `audit_service.log`（复用既有留痕链）；
5. 跑 `compiler.run_validations(package_id)`——此时会有一批 error/warn（如 `QUOTE_REQUIRED` 的模板豁免分支落在 §6.1 前，仍会有 `TEMPLATE_FALLBACK_SIGNOFF` error），**这是特性不是缺陷**：UI 明示"模板条目尚无招标文件依据、未签批不得冻结"。

`ProjectCreate`（`schemas/project.py`）增加可选 `base_template_id`：前端新建项目弹窗选择后，创建成功即自动调用 instantiate。

### 4.3 与既有 compile 流程的关系

- `compile_rules` 默认行为不变（`mode='replace'`）：无模板的项目仍走"上传文件→编译"的现行唯一路径。
- `CompileRequest`（`schemas/rules.py`）增加 `mode: 'replace' | 'merge'`（默认 replace）。项目已有模板来源草稿包时，前端提示选 merge（§八）。
- **演示模式（S0 的价值）**：instantiate → 逐条签批（把模板判据确认为"演示用判据"）→ confirm → freeze → 添加演示投标人并评分。冻结前的全部卡点（校验器 error、`_blocking_items`、签批）**照常生效**，因此演示包与真实包走同一条代码路径——演示数据永远不会意外变成"未经签批的执行依据"。

## 五、逐条覆盖机制（核心）

### 5.1 触发与两阶段结构

`POST /projects/{id}/rules/compile`，body `{document_id, mode: 'merge'}`：

- **阶段 A（复用现行代码，不改）**：`compiler.compile_rules` 完整跑一遍 LLM 抽取 + 证据核验 + 六态分诊，但产物**不直接替换模板包**，而是落成一个**临时草稿包**（`origin='document'`，包级新增列 `merge_target_id` 指向模板包）。选择临时包方案的理由：`_persist_criterion`、`_verify_and_backfill`、六态分诊等既有实现全部原样复用，零改动。
- **阶段 B（新增 `backend/app/rules/merger.py`）**：对两包 criteria 做匹配 → 生成**匹配提案**（只读，不对模板包做任何写操作）→ 人工确认 → 执行覆盖 → 临时包标记 superseded。

### 5.2 匹配策略：确定性优先，LLM 兜底，人工终审

**第一层（纯代码，`merger.py`）**：

1. 硬过滤：`category` 与 `score_type` 必须相等（veto↔veto、formula↔formula、subjective↔subjective…）；price 类天然 1:1（`load_criteria_for_snapshot` 已假设每包单条 price formula）。
2. 名称精确匹配：经 `app/parsing/normalize.py` 归一化后相等 → `match_method='exact'`，similarity=1.0。
3. 名称相似度：归一化字符 bigram Jaccard ≥ 0.55 或 `difflib.SequenceMatcher.ratio() ≥ 0.75` → `match_method='deterministic'`。

**第二层（LLM 辅助，新增 `rules/prompts.py` 的 `MATCH_SYSTEM_PROMPT`）**：

- 输入：模板条目清单（code+name+category+max_score+levels 摘要）× 未匹配编译条目清单（id+name+quote 前 120 字），要求输出 1:1 配对 + confidence + 一句话理由。
- **封闭菜单**：LLM 只能在给出的候选里选、不得发明新配对——与 tender-evaluation-assistant"把封闭菜单交给模型"以及 RPF Agent 自身"weight 永不进 prompt"是同一条约束思路。
- 输出经 Pydantic 契约（`MatchProposal`）校验；confidence < 0.5 的配对直接丢弃，降级为人工手工配对列表（开放问题 4）。

**第三层（人工终审，产品原则）**：**任何覆盖在人工确认前不生效。** 匹配提案全部进入 UI 审核队列；LLM/相似度结果即使 similarity=1.0 也只是"预勾选"。

### 5.3 覆盖语义

人工确认一对 (模板条目 T，文档条目 D) 后，`merge_service.apply_override(T, D, actor, reason)`：

1. **字段级替换**（T 行内就地更新，不新增行）：`name / description / max_score`；levels **全删全建**（复用 `rule_service.set_levels:306` 的实现方式）；`CriterionCheck` 全删全建；price 类替换 `PriceFormula` 参数。**`code` 保持 = T.template_code 不变**。
2. **来源升级**：`T.origin='document'`；`T.p_source = D.p_source`；`T.source_node_id / source_page / source_quote = D 的溯源四件套`；`T.status = D.status`（**继承六态分诊结果**——文档证据没核验通过就仍是 needs_input/ambiguous，覆盖不会把未核验的引用"洗白"成 verified）；`template_code / template_hash / library_version` **保留**（记住"我从哪个模板条目来"）。
3. **留痕**：`T.override_json = {overridden_template_code, match_method, similarity, document_node_id, document_quote, won_source: D.p_source, lost_source: 'P5', by, at, reason}`；`override_records` 插一行 `action='override'`；`ReviewRecord` 插一行（复用既有留痕链）。
4. **D 行不复制进模板包**，只留在临时编译包中（临时包保留不删）：T 的 override_json 已引用其 node_id/quote，`override_records.document_criterion_id` 指向临时包行 id 供回溯。避免同一语义双行并存污染 `TOTAL_SCORE` / `CODE_DUPLICATE`（开放问题 3）。

### 5.4 未匹配条目的处置

| 情形 | 默认动作 | 记录 |
|---|---|---|
| 模板条目未被任何文档条目匹配 | **保留**：`origin='template'`、`status='needs_signoff'`，UI 标注"未覆盖-模板兜底" | 进签批队列 |
| 模板条目被人工判定"本项目无此项" | `status='retired'`：不进快照、不参与 `TOTAL_SCORE`/权重校验 | `override_records action='drop_template'` + reason 必填 |
| 编译条目未匹配任何模板条目 | **追加**进模板包：`origin='document'`，code 沿用编译编号，六态分诊结果照带 | `override_records action='append_document'` |
| 高相似但人工拒绝配对 | 模板条目照常进签批队列；编译条目照常追加为 document 来源；两者并存，由人工后续 retire 其一 | 两条 override_records |

### 5.5 匹配提案 API

```
GET  /rules/packages/{merge_pkg_id}/match-proposal
     → {pairs: [{pair_id, template_criterion, document_criterion,
                 match_method, similarity, confidence, rationale}],
        unmatched_template: [...], unmatched_document: [...]}

POST /rules/packages/{merge_pkg_id}/match-proposal/resolve
     body {decisions: [{pair_id | document_criterion_id,
                        action: 'override' | 'reject' | 'drop_template',
                        template_criterion_id?, reason}], actor}
     → 执行 §5.3/§5.4，返回合并后的草稿包 id
```

## 六、合规与签批

### 6.1 校验器扩展（`rules/validators.py`）

在现有确定性校验器（QUOTE_REQUIRED / VETO_SCORED / PRICE_WEIGHT_RANGE / TOTAL_SCORE / LEVEL_* 等）基础上：

1. **`QUOTE_REQUIRED` 按 origin 分支**：仅对 `origin != 'template'` 的条目要求逐字原文；模板条目豁免（它们本来就没有原文），其"依据缺失"由第 2 条承担。
2. **新增 `TEMPLATE_FALLBACK_SIGNOFF`（error）**：`origin='template'` 且 `signoff_json IS NULL` 且未 retired → "评分项「X」为模板兜底（P5），招标文件未规定；未签批不得冻结"。这是调研结论四与"执行链路只认 P0–P4 来源标记"的直接工程化。
3. **新增 `TEMPLATE_FALLBACK_ESSENTIAL`（S1 为 warn，S2 转 error）**：`origin='template'` 且（`is_veto` 或 `category IN ('qualification','compliance','price')`）→ 即使签批，也要求签批 reason 写明启用理由，并在覆盖报告/冻结报告中单列。对应"合规红线：治理价格/否决/资格的条目不宜以模板兜底形态长期存在"。
4. **快照升级 `rule_package/v2`**：`freeze.build_snapshot` 与 `load_criteria_for_snapshot`（`rule_service.py:172`）为 criteria dict 增加 `origin / template_code / template_hash / library_version / p_source / signoff / override` 字段；`retired` 条目**排除在快照外**（总分口径自动正确）。v1 快照保持可读（字段缺省处理），不破坏既有数据。

### 6.2 签批动作

- `POST /rules/criteria/{id}/signoff`，body `{reason}`（`min_length=1`，同 `accept_criterion` 的理由强制）：仅对 `origin='template'` 且 `status='needs_signoff'` 生效；写 `signoff_json={by,at,reason}`、置 `status='verified'`、`ReviewRecord(action='signoff')` + audit log。
- **系统故意不提供"全部签批"**——与 `accept_criterion` 不提供"全部采纳"是同一个产品立场：签批是逐条责任，不是批量确认。
- **签批 ≠ 覆盖**：签批后的条目 origin 仍是 template，冻结包与评分报告里**永远**显示"模板兜底（已签批：签批人/时间/理由）"。

### 6.3 覆盖率报告与红线

`GET /rules/packages/{id}/coverage` →

```json
{"total": 24, "document_backed": 19, "template_fallback_signed": 3,
 "template_fallback_pending": 2, "retired": 1, "manual": 0,
 "by_category": {"qualification": {...}, "technical": {...}},
 "essential_uncovered": ["T1.2", "T3.1"],
 "price_covered": true, "veto_covered_ratio": 0.83}
```

红线判定**集中在既有 freeze 路径**：`freeze_package`（`rule_service.py:460`）已有"重跑校验 + `_blocking_items`"双闸门，新校验器 error 自动纳入，**无需改 freeze 代码**（校验器 error → 422，blockers 已透传前端 Modal）。

### 6.4 评分输出标注

- `score_records` 新增列 `criterion_origin String(16)`、`template_code String(64)`；`scoring_service.execute_run` 已在每个 criterion dict 注入 `rule_version` / `package_content_hash`（`scoring_service.py:155`），同处注入 origin；`_upsert_score`（`:308`）落库时带上。
- 评分矩阵与报告逐项显示：`依据：招标文件 第n页「…（逐字核验通过）」` vs `模板兜底（已签批：{actor} {时间}）`。实现方式：报告渲染时读**快照 v2**（自带全部溯源字段），不回查业务表——与"评分只认快照"的既有原则一致。
- **纵深防御**：`scoring_service` 执行前检查快照，若存在 `origin='template'` 且无 signoff 的条目，直接 `ValidationFailed` 拒绝执行（正常应在 freeze 已拦，此处防快照被绕过构造）。

## 十一、开放问题（附推荐）

1. **库存储：JSON 文件 vs DB 表？** 推荐 JSON 文件随仓库发布（S0–S2 不建 `rule_templates` 表）：模板需要代码评审与 git 溯源，tender-evaluation-assistant 已验证此形态；出现"多租户自定义库"需求时再加 DB 表 + loader 双源。
2. **status 是否新增 `needs_signoff` / `retired`？** 推荐新增：复用 `needs_input` 会混淆"文档没说清"与"文档没规定、用模板兜底"两种法律含义不同的状态。
3. **被覆盖的编译条目行是否保留？** 推荐不复制进模板包、留在外部编译临时包中，`override_records.document_criterion_id` 指过去，避免双行并存污染总分与编号校验。
4. **LLM 匹配不可用时的降级？** 确定性匹配照常出提案；其余全部进"人工手工配对"列表（UI 提供两侧下拉自选配对），不阻塞主流程。
5. **同一项目能否更换基线模板？** 推荐 S0 不支持（instantiate 仅限无规则包的新项目）；已有包换模板走 `new_version` + 手工增删，避免模板替换引发批量覆盖语义。
