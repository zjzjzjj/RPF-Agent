## 0. 一句话方案

在评分体系**旁边**加一条独立的「证书核验」工作流：解析完成后从投标文件抽取证书清单 → 评委在认E云网页人工查询 → 结果+截图回填落库 →（P2 经授权后）作为外部事实只读进评分事实链。**P0 全程不依赖任何外部 API、不改评分代码。**

## 2. 总体架构（回答「放哪 / 何时 / 是否与评分一起」）

```
解析(parse_document)
   └─► [P0] 不挂钩：清单由前端打开页面时显式「刷新」生成（幂等）
                （升级路径：解析完成回调自动刷新，见 §11-2）

评标准备期（规则冻结后、发起评分前）★核验窗口
   └─► 评委打开「证书核验」页 → 刷新清单 → 逐本去认E云查询 → 回填+截图

评分运行(evaluate)
   └─► P0：完全不感知核验表存在（零耦合）
        P2：只读 SELECT 核验表 → 注入 facts → 三态消费（见 §7）
```

| 问题 | 答案 |
|---|---|
| 放在哪（后端） | 新增 `services/cert_verify_service.py` + `api/cert_verify.py`，与评分链平行，不 import 引擎 |
| 放在哪（前端） | **新导航项「证书核验」**（`AppShell.NAVIGATION` 插在「规则库管理」与「评分结果」之间）+ 新路由 `/p/:pid/certs` + 新页面 `CertVerify.tsx`。⚠️ 修正上轮说法：`EvidenceWorkbench` 是单评分项页面（路由 `evidence/:sid`），不适合放项目级清单 |
| 何时开始 | 清单生成=打开页面/点刷新时；核验动作=评委人工触发（评标准备期）；**评分永不等待核验** |
| 后端与评分一起跑吗 | 同进程、同 job 队列，但**不是同一个 job**；P0 甚至没有 job（同步接口，快路径 <2s）；互不阻塞 |
| 前端与评分放一起吗 | 不放一起：核验是评审操作（在自己的页面），评分结果页 P2 只加一行摘要 Tag |

## 3. 数据模型

### 3.1 新表 `certificate_verifications`

```python
class CertificateVerification(Base):
    __tablename__ = "certificate_verifications"

    id: int                          # PK
    project_id: str                  # FK projects.id, index
    bidder_id: int                   # FK bidders.id, index
    # —— 抽取事实（refresh 更新，人工回填不覆盖）——
    cert_name: str                   # 原始证书名（"ISO/IEC 20000-1:2018"）
    cert_normalized: str             # normalize_cert 口径（ISO9001/ISO27001/ISO20000/CMMI…）
    family: str                      # iso|cma|ccc|cnas|cmmi|other（路由，见 §5.2）
    cert_number: str | None          # 证书编号（页级唯一绑定，绑定不了为 None 待补录）
    valid_until: str | None          # 抽取的有效期（YYYY-MM-DD）
    source_pages: dict | None        # {"document_id": n, "page_no": [..]} 抽取锚
    stale: bool                      # refresh 后不在最新清单中 → True（灰显，不删）
    # —— 核验结果（人工/P1 Provider 写入，refresh 不碰）——
    provider: str                    # manual|mock|official_api
    status: str                      # pending|verified_valid|verified_invalid|unknown|not_supported
    mismatch_kind: str | None        # number_not_found|status_abnormal|holder_mismatch|expired
    platform_status: str | None      # 平台状态原文（有效/暂停/撤销/注销/查无此证…）
    holder_name: str | None          # 平台显示持证单位（与投标人名比对）
    platform_valid_until: str | None # 平台显示有效期
    provider_result: dict | None     # 回填/返回全量原文（审计）
    screenshot_path: str | None      # 查询截图（相对 upload_dir）
    note: str | None                 # 人工理由（必填，见 API）
    operator: str | None             # 回填人（X-Actor）
    queried_at: datetime | None
    created_at: datetime
    updated_at: datetime

    __table_args__ = (
        UniqueConstraint("bidder_id", "cert_normalized", "cert_number",
                         name="uq_cert_verify_key"),
        CheckConstraint("status IN ('pending','verified_valid','verified_invalid',"
                        "'unknown','not_supported')", name="cert_status_valid"),
        CheckConstraint("provider IN ('manual','mock','official_api')",
                        name="cert_provider_valid"),
        # mismatch_kind 允许 NULL；枚举约束同理列出
    )
```

要点：

- **唯一键** `(bidder_id, cert_normalized, cert_number)`：同一本证书一行；`cert_number` 为 NULL 时 SQLite 唯一约束对 NULL 不去重——清单构建时对「编号缺失」的行用 `cert_number=""`（空串）占位参与唯一键，回填补录编号时若撞键则合并（保留已有核验结果，更新编号）。
- **两段式字段**：抽取段（refresh 可重写）与核验段（只有回填/Provider 可写）分离，保证「刷新清单不丢人工核验」。
- **不删行**：refresh 只 upsert + 置 `stale`，历史核验永远可追溯（审计口径）。

### 3.2 状态机

```
                清单生成
                   │
                   ▼
               pending ──────────────┐
                   │                 │
     人工回填/P1 API 查询             │ CMMI 等非认E云族（生成时直接标）
                   │                 ▼
       ┌───────────┼──────────┐ not_supported ──(仍可人工回填覆盖)
       ▼           ▼          ▼
verified_valid  verified_invalid  unknown
   (有效)      (查无/暂停/撤销/   (查不到/网络失败/
                单位不符/过期)     平台不可用——不猜)
```

不变量（沿用仓库既有口径）：

1. `unknown` ≠ 不符合——「机器看不见≠不符合」；
2. `verified_invalid` 在 P2 也只产生**疑问/建议否决**，绝不自动否决、绝不自动清零（决策 0017 口径）；
3. `not_supported` 只是 Provider 层提示，人工回填永远可覆盖。

### 4.2 证书清单构建（`build_cert_list(bidder_id)`）

**不复用 `build_inventory()`**（它要开 PDF 解析合同表，重且慢）；只抽证书：

```
读取该投标人全部已解析文档的 DocumentPage（复用 automatic_scoring_service
的读取模式：parse_status ∈ (parsed, degraded)、逐文档降级，但不抛 LLMError——
读不到就返回已读到的部分）
        │
        ▼
material_inventory.certs_from_pages(pages)      # 现 _certs_from_pages 升级为公开
  + material_inventory.maturity_certificate_details(pages)   # CMMI 成熟度评估
  + material_inventory.certificate_numbers(page_text) 逐页
        │
        ▼
编号绑定：证书记录的 pages 内若恰有 1 个编号 → 绑定；
         ≥2 个 → 不猜，cert_number="" 待人工补录
        │
        ▼
family 路由（§5.2）→ upsert（抽取段写入；核验段保留）
        │
        ▼
最新清单未出现的旧行 → stale=True（不删）
```

性能预算：数百页文本的正则扫描 + SQLite 读写，目标 <2s/家（无 PDF 打开、无 LLM、无网络）。超时则升级为 job（§11-3）。

### 4.3 人工回填（`manual_verify(verification_id, ...)`）

输入 → 服务端计算 `mismatch_kind`（优先级从高到低，取首个命中）：

| 优先级 | 条件 | mismatch_kind | status 影响 |
|---|---|---|---|
| 1 | `platform_status` 含「查无 / 不存在」 | `number_not_found` | 强制 `verified_invalid` |
| 2 | `platform_status` ∈ {暂停, 撤销, 注销, 过期} | `status_abnormal` | 强制 `verified_invalid` |
| 3 | `holder_name` 归一化 ≠ 投标人名（去空白/标点/「股份有限公司」等后缀后仍不互含） | `holder_mismatch` | 强制 `verified_invalid` |
| 4 | `platform_valid_until` < 今天 | `expired` | 强制 `verified_invalid` |
| — | 以上皆不中 | NULL | 按人工选择的 status |

- 人工选择的 `status` 若与上表强制结果冲突（如选了 valid 但单位不符）→ **以服务端计算为准**，响应里返回 `corrected: true`，前端 toast 提示。
- `note` 必填（min_length=1）；`status ∈ {verified_valid, verified_invalid}` 时 `screenshot` 必填（无截图的「有效」结论不收——对应招标文件「无查询截图不予计分」的证据要求）；`unknown` 截图可选。
- 写审计：`audit_service.log(project_id, actor, "cert.verify_manual", "cert_verification", str(id), {status, mismatch_kind, platform_status})`。

### 4.4 API 契约

| Method | Path | 说明 |
|---|---|---|
| GET | `/projects/{pid}/certs/summary` | 按投标人统计 `[{bidder_id, name, total, pending, valid, invalid, unknown, not_supported, stale}]`，前端左侧列表用 |
| GET | `/bidders/{id}/certs` | 该投标人核验行列表（只读） |
| POST | `/bidders/{id}/certs/refresh` | 同步重建清单（幂等），返回最新列表；actor 走 `get_actor` |
| POST | `/certs/{vid}/manual` | multipart：`status/platform_status/holder_name?/platform_valid_until?/note` + `screenshot?` 文件 |
| GET | `/certs/{vid}/screenshot` | FileResponse（png/jpg，`Cache-Control: max-age=86400`） |

约定：

- 错误信封沿用 `errors.AppError`（`NotFound`/`ValidationFailed`/`Conflict`）；
- `refresh` 与 `manual` 都写审计（`cert.list_refresh` / `cert.verify_manual`）；
- 截图落盘 `config.upload_dir() / "cert_verify" / str(vid) / 文件名`，**类型白名单 png/jpg/jpeg + 单文件 ≤5MB**（不走 `upload_guard`——那是 zip 专用）；文件名服务端生成（防路径穿越，`Path(name).name` 惯例同 `ingest_service`）。

## 6. 证书族路由（清单生成时的 `family`）

| 归一键模式 | family | 认E云可查 |
|---|---|---|
| ISO* / GB/T（管理体系） | `iso` | ✅ |
| CMA（检验检测资质） | `cma` | ✅ |
| CCC / 强制性产品 | `ccc` | ✅ |
| CNAS（实验室认可） | `cnas` | ✅ |
| CMMI / CSMM / 能力成熟度 | `cmmi` | ❌ → `status=not_supported`（仍可人工回填） |
| 其余（信息系统集成资质等） | `other` | 按平台实测，P0 先标 `pending` 由人工判断 |

> 依据调研报告 §2.2：CMMI 属工信部体系，不在 CNCA 平台——不路由会产假阴性。

## 7. P2 评分接线设计（本次只写设计，不实现）

```
scoring_service（算 cert_sections 处，约 L823）
   └─+ SELECT certificate_verifications WHERE bidder_id=?
      → facts["cert_verify"] = {ISO9001: {status, mismatch_kind, queried_at}, …}
        │
        ▼
objective.py 证书计数分支（消费，改动点最小化）：
   verified_valid   → 该本 backing 升级为强证据（等价 section_ok=True 路径）
   verified_invalid → conflict=True + doubt=True（疑问转人工/报告建议否决）
   无记录 / unknown → 现有三态逻辑逐字不变
```

- 开关 `BID_EVAL_CERT_VERIFY_FEED_SCORE` 默认 0；启用前跑 `eval_suite --validate` 确认 ground truth 项目不回退；
- 绝不接：价格引擎、基准价剔除、veto_flag 自动置位、无效标剔除（无效标政策仍暂缓）。

## 11. 遗留决策点（不阻塞 P0）

1. **工作台是否加「证书核验」阶段卡**：会破 `test_workbench_optional.py` / `test_db.py` 的三阶段断言（两处需同步改），收益是流程可见性——建议 P2 与报告附表一起做。
